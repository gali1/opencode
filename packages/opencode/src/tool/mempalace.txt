Persistent AI memory system combining MemPalace (structured verbatim storage, knowledge graph) with Rekal (typed memories, lifecycle management, hybrid search with configurable weights).

## Session Start — Do This First

Call build_context with your current task before exploring the codebase. This loads relevant memories, conflicts, and timeline in one call.

## Two Memory Layers

### Layer 1: MemPalace (drawers — verbatim storage)
- search: Semantic search over stored drawers
- store: File verbatim content into a wing/room
- status, list_wings, list_rooms: Palace overview
- kg_add, kg_query, kg_invalidate: Knowledge graph entity relationships
- diary_write, diary_read: Session diary

### Layer 2: Rekal Engine (structured memories with lifecycle)
- memory_store: Store a typed, tagged, project-scoped memory
- memory_search: Hybrid search (BM25 + vector + recency) with configurable weights
- memory_update: Edit content, tags, or type of an existing memory
- memory_delete: Remove a memory by ID
- memory_supersede: Replace a memory while preserving history via links. ALWAYS prefer this over delete + store.
- memory_link: Connect memories (supersedes, contradicts, related_to)
- build_context: One call that returns relevant memories + conflicts + timeline. USE THIS AT SESSION START.
- memory_conflicts: Find contradicting memory pairs
- memory_health: Database stats (counts by type, project, active vs superseded)
- memory_similar: Find memories similar to a given one
- memory_topics: Topic summary grouped by type
- memory_timeline: Chronological view with optional date range
- memory_related: All links to and from a memory
- set_config: Set per-project scoring weights (w_fts, w_vec, w_recency, half_life)

### Verification
- contradiction_check: Check if a statement contradicts existing KG facts. Use BEFORE kg_add.
- fact_check: Validate a claim against KG + stored memories. Returns confidence and verdict.
- multi_hop: Find indirect entity relationships via BFS through the knowledge graph.

## When to Use Which Layer

Use **Rekal engine** (memory_store, memory_search, memory_supersede) for:
- User preferences and decisions
- Architecture and conventions discovered during work
- Procedures and workflows
- Any knowledge that should survive across sessions

Use **MemPalace native** (store, search) for:
- Verbatim conversation content
- Raw file summaries and code snippets
- Content that benefits from MemPalace's wing/room hierarchy

Use **build_context** at session start — it searches the Rekal engine and returns everything in one call.

## Storing Memories — Critical Rules

### ALWAYS search before storing
```
1. memory_search(query="<topic>", limit=5)
2. Read results:
   - Exact duplicate → do nothing
   - Same topic, outdated → memory_supersede(old_id="<id>", content="<new>")
   - Same topic, contradicts → memory_supersede(old_id="<id>", content="<corrected>")
   - No match → memory_store(content="<fact>", memory_type="<type>", tags=[...])
```
Two memories about the same topic must NEVER coexist. Supersede, don't duplicate.

### Distill before storing
NEVER store raw dialogue. Extract the durable fact, compress it.
- Drop: articles, filler, hedging, pleasantries
- Keep: technical terms, proper nouns, versions, reasons, causality
- One memory = one distilled fact, 1-2 sentences max

### memory_type values
- fact: Objective truth about code/systems/APIs
- preference: How user wants things done
- procedure: Step-by-step workflow
- context: Current project state (decays via recency scoring)
- episode: Notable event, debugging session

### tags: 2-4 specific tags, never generic ("code", "project")

## Hybrid Search Scoring

memory_search combines three signals:
- BM25 keyword relevance (w_fts, default 0.4)
- Vector semantic similarity (w_vec, default 0.4)
- Recency decay (w_recency, default 0.2, half_life 30 days)

Override per-search: memory_search(query="...", w_fts=0.8, w_vec=0.1, w_recency=0.1)
Override per-project: set_config(project="myproj", key="w_fts", value="0.6")

## Validation (critical)

NEVER blindly trust retrieved memory. Always:
1. Use fact_check on claims you're uncertain about
2. Use contradiction_check BEFORE kg_add or memory_store
3. Cross-reference against current file state when memory age is unknown
4. If memory contradicts current code, trust the code

## What NOT to Store

- Transient state ("currently editing X", "tests passing")
- Trivially re-discoverable facts (line numbers, file sizes)
- Vague platitudes ("user likes clean code")
- Secrets, API keys, passwords — never
- Things already in CLAUDE.md or AGENTS.md

## Progressive Trust Model

- Early session: build_context first, validate memories against files
- Mid-session: trust verified memories, contradiction_check on new facts
- Late session: use memories as primary source, validate only when uncertain
